# 런북 검색 평가 데이터

`rag-dataset.json`은 기존 규칙 기반 런북 선택과 이후 RAG 검색을 비교하기 위한
고정 평가 입력과 정답 근거다. 실행기는 `run_rag_evaluation.py`이며 결과는 별도 실행 폴더에 저장한다.
기존 전체 대화 평가셋인 `dataset.json`과 baseline 측정 결과는 그대로 유지한다.

## 평가 범위

검색에 전달할 질문과 관측 정보를 고정한 **검색 구성요소 평가**다.
`/chat`에 질문만 보내는 전체 흐름 평가와 구분한다.
현재 그래프는 사용자 질문으로 바로 문서를 찾지 않고 모니터링 수집 결과의
`status`와 `alerts`를 `_classify_incident_type()`에 전달한다.
처음 일치한 키워드에 해당하는 문서 하나를 선택하고, 일치하지 않으면 `db-down`을 선택한다.

따라서 질문만 바꿔 실제 `/chat`을 실행하면 고정 모니터링 알림이 반복되어
동의어 검색 능력이나 6종 런북 전체를 충분히 평가할 수 없다.
이번 데이터는 동일한 질문과 관측 정보를 양쪽 검색 방식에 제공하고,
현재 방식이 질문을 사용하지 않는다는 점도 비교 조건에 기록한다.
그 결과는 검색 정책 전체의 차이이며, 임베딩 알고리즘만의 효과를 분리한 실험은 아니다.

모든 `observations`는 검색 평가용 합성 입력이다. 일부는 기존 알림과 유사하지만
실제 MCP Tool 응답이나 운영 관측 결과가 아니다.
`data/monitoring.json`을 수정하거나 가상 장애를 실제 서비스에 적용하지 않는다.
등록 시스템 이름을 재사용해 대상 이름의 영향을 줄였으며,
DB 중단 등 현재 샘플에 없는 증상도 합성 입력으로 포함했다.

## 사례 구성

| 분류 | 사례 | 수 | 기대 문서 또는 행동 |
|---|---|---:|---|
| 정확한 용어 | R01–R06 | 6 | CPU, 메모리, 디스크, 지연, 네트워크, DB 문서 각 1개 |
| 자연어·동의어 | R07–R12 | 6 | 동일한 6종 문서를 다른 표현에서도 회수 |
| 복합 증상 | R13 | 1 | `cpu-spike`, `memory-leak` |
| 복합 증상 | R14 | 1 | `network-timeout`, `cpu-spike` |
| 복합 증상 | R15 | 1 | `high-latency`, `disk-full` |
| 복합 증상 | R16 | 1 | 같은 시스템의 `memory-leak`, `disk-full` |
| 해당 절차 없음 | R17–R20 | 4 | 인증서 갱신, JWT 키 교체, 시점 복원, 환불: 근거 부족 |
| 경계 사례 | R21 | 1 | 풀 조정 기준은 `high-latency` |
| 경계 사례 | R22 | 1 | 힙 객체 조사는 `memory-leak` |
| 경계 사례 | R23 | 1 | CPU·memory·disk 키워드가 있어도 정상 관측이면 채택하지 않음 |
| 정보 부족 | R24 | 1 | 증상을 확인하고 특정 문서를 확정하지 않음 |

총 24건 중 문서 회수가 필요한 사례는 18건, 문서 미채택 기대 사례는 6건이다.
미채택 사례는 근거 부족 5건과 확인 필요 1건으로 나누어 보고한다.
복합 증상의 문서 목록 순서는 정답 순위가 아니다.
이번 평가에서는 `allowed_extra_document_ids`가 모두 비어 있다.
직접 요청된 절차를 뒷받침하는 문서만 관련 문서로 판정한다.

## 정답 근거의 형태

각 사례는 다음 정보를 포함한다.

- `input`: 사용자 질문과 고정 관측. 검색기에 제공할 수 있는 입력은 이 부분이다.
- `expected_action`: 문서 회수(`retrieve`), 근거 부족(`abstain`), 확인 필요(`clarify`).
- `required_document_ids`: 반드시 회수해야 하는 런북의 파일 이름에서 확장자를 뺀 ID.
- `evidence`: 문서별 필수 절차 번호, 원본 줄 번호, 해당 줄의 원문.
- `label_rationale`: 해당 문서를 정답으로 정한 이유 또는 문서가 부족한 이유.

`corpus`에는 6개 원본 파일의 경로·MCP URI·SHA-256이 들어 있다.
정답은 현재 프로그램의 선택 결과가 아니라 실제 문서가 제공하는 절차를 기준으로 작성했다.
`expected_*`, `evidence`, `label_rationale`을 검색 프롬프트나 색인에 넣으면 안 된다.
RAG 색인 대상은 `data/runbooks/*.md` 6개이며 평가 파일은 포함하지 않는다.

필수 근거는 짧은 정답 답변을 외우게 하기 위한 문구가 아니다.
문서 또는 검색 청크가 필요한 절차를 제공하는지 판단하는 기준이다.
예를 들어 `cpu-spike`의 90% 지속 조건, `high-latency`의 5분 조건,
`memory-leak`의 재시작이 임시 조치라는 설명을 답변에서 무조건적인 행동으로 바꾸면
문서 검색 성공과 별개로 근거 사용 실패다. 실행하지 않은 조치를 수행했다고 표현해서도 안 된다.

## 4번 측정 단계에서 사용할 비교 조건

1. Before는 기준 커밋 `1601a95`의 기존 분류 함수를 사용한다.
   `observations`를 각각 `{"source": "monitoring", "data": observation}`으로 감싸
   전달하고, 선택한 ID의 문서를 기존 MCP 경로로 읽는다.
   query를 활용하지 않는 기존 동작과 기본 `db-down` 선택을 그대로 둔다.
2. After는 같은 질문·관측·코퍼스를 입력으로 사용한다.
   검색 후보와 최종 채택 문서를 분리해 기록한다. 후보가 존재해도
   무관한 문서를 근거로 채택하지 않는 처리가 미조회 사례의 평가 대상이다.
3. 한 질문마다 입력, 반환 문서 ID·본문 또는 청크, 채택 문서 ID,
   오류, 경과 시간, 사용 모델·색인·검색 설정을 저장한다.
   근거가 기록되지 않은 항목은 관측 불가로 표시한다.
4. 데이터셋 파일 해시와 코퍼스 해시를 함께 기록한다.
   Before/After 측정 사이에 정답이나 원본 문서를 바꾸면 버전을 올리고 양쪽을 다시 측정한다.
5. 초기 연결·색인 작성 시간과 준비된 상태의 검색 시간을 분리한다.
   기존 `parallel_elapsed`는 서버 탐색 등을 제외하므로 검색 전체 시간과 혼용하지 않는다.
   이 평가에서는 검색 입력 준비 이후부터 본문 수집 완료까지 별도 시간을 측정한다.

실행 방법은 아래와 같다. 출력 폴더가 이미 있으면 덮어쓰지 않고 중단한다.

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m eval.run_rag_evaluation \
  --phase before --output eval/results/rag-before --repetitions 3
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m eval.run_rag_evaluation \
  --phase after --output eval/results/rag-after-8b --repetitions 3
```

Before는 보존한 분류 함수와 실제 MCP 문서 읽기를 사용한다.
After는 서버와 동일한 `build_retriever()`를 사용한다.
실행기는 외부 LangSmith 추적을 끄고 정답을 제외한 `input`만 검색기에 전달한다.
`manifest.json`에는 실행 코드 해시·데이터셋 해시·코퍼스·모델 이름·색인 시간을,
`raw.jsonl`에는 사례별 문서 본문·후보 점수·선택 이유·오류·시간을 저장한다.
`summary.json`의 점수는 전체 응답 품질이나 운영 정확도가 아닌 검색 구성요소 점수다.

현재 원문을 그대로 컨텍스트로 공급하므로 자동 근거 지표는
`evidence_exact_recall`(필수 원문 절차 포함 비율)이다.
답변이 원문의 의미와 조건을 정확히 사용했는지는 별도로 검토해야 한다.
출력 오류는 종료 코드 1로 알리고 이미 기록한 결과는 보존한다.

전체 그래프의 라우팅·시스템별 근거 연결·최종 답변·비용 평가는
기존 `dataset.json`의 전체 흐름 평가와 후속 통합 평가에서 따로 확인한다.

## 점수와 분모

문서 회수 18건에 대해 필수 문서 집합을 G, 실제 채택 문서 집합을 R,
허용 문서 집합을 A = G + allowed_extra_document_ids로 둔다.

- 문서 회수율: `|R ∩ G| / |G|`.
- 채택 문서 관련 비율: `|R ∩ A| / |R|`. 성공 응답이지만 빈 결과이면 이 평가 규약에서는 0.
- 완전 회수: 필요한 문서가 모두 포함되었는지(`G ⊆ R`).
- 필수 근거 회수율: 실제 컨텍스트에 의미와 조건이 보존된 필수 절차 수 / 필요한 필수 절차 수.

성공 실행에서 빈 결과라면 회수율도 0이다. 오류·미실행·관측 불가는 별도 상태로 기록한다.
관측된 사례의 평균과 함께 전체 대상 수·실행 수·오류 수·관측 가능 수를 보고하고,
일부 실패를 제외한 점수를 전체 성공률처럼 제시하지 않는다.
문서만 찾고 필요한 절차가 청크에서 빠진 경우를 문서 회수율만으로 합격시키지 않는다.

문서 미채택 기대 6건은 회수율의 분모에서 제외한다.
성공적으로 검색한 뒤 아무 문서도 근거로 채택하지 않은 비율을 따로 보고한다.
검색 오류나 타임아웃으로 결과가 없는 것은 올바른 미채택이 아니다.
확인 질문과 근거 부족 안내를 실제 답변에 표현하는지는 별도의 답변 평가 항목이다.

RAG가 순위를 제공하면 Recall@1과 Recall@3을 별도로 기록한다.
청크를 문서 ID로 변환한 뒤 최초 등장 순서로 중복 제거하고 k개를 취한다.
기존 문서 선택에는 검색 순위가 없으므로 공통 비교는 문서 집합 지표를 사용한다.
6종 문서를 모두 반환하는 방식은 회수율만 높일 수 있으므로 관련 비율을 함께 제시한다.

## 해석 범위

이 자료는 코드와 문서를 보고 작성한 수작업 회귀 평가셋이다.
블라인드 테스트셋이나 실제 사용자 질의 분포를 대표하는 자료는 아니다.
질문을 보고 구현·임계값을 조정했다면 그 사실을 보고한다.
반복 실행은 지연 변동을 확인하는 용도이며 독립 질문 수는 여전히 24개다.
데이터셋의 `measurement_status: not_run`은 측정 전 고정 파일의 상태다.
실제 실행 여부와 결과는 파일을 바꾸지 않고 각 실행 폴더의 manifest와 원시 기록으로 판단한다.
