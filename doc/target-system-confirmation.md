# 대상 시스템 확인

v2 진단 경로는 모니터링 전에 사용자 요청의 대상을 확인한다.
등록 목록은 `data/monitoring.json`이며, 기본 시스템으로 대체하지 않는다.

| 입력 | 동작 |
|---|---|
| `payments-service CPU 급증 진단` | payments-service만 조사 |
| `gateway-service와 log-service 장애 진단` | 두 시스템을 각각 한 번 조사 |
| `CPU 급증 원인 진단해주세요` | 등록 시스템 선택 요청 |
| `payments-service-old 장애 진단` | 부분 일치로 조사하지 않고 선택 요청 |
| `결제 서비스 장애 진단` | payments-service를 추천하되 선택 전에는 조사하지 않음 |
| `payments-service 말고 cache-service 진단` | 배제 표현의 범위를 추측하지 않고 재확인 |
| `payments-service는 빼 주세요. cache-service 진단` | 배제 표현의 조사·띄어쓰기 변형도 재확인 |
| `payments-service에서 ERR_CONNECTION_RESET 오류 진단` | 오류 코드를 시스템으로 취급하지 않고 payments-service 조사 |
| `payments-service의 p95-latency 원인 진단` | 분위수 지표를 시스템으로 취급하지 않고 payments-service 조사 |
| `CPU 급증 대응 절차를 찾아줘` | 실제 런북 제목을 지정한 조회는 관측 없이 RAG 검색 |

## 확인 후 이어가기

확인 대기 질문은 기존 SQLite 저장소의 `pending_targets` 테이블에 스레드별로 보관한다.
시스템 버튼을 누르거나 `gateway-service와 log-service`처럼 이름들을 입력하면
원래 질문의 증상을 유지한 채 진단한다. 원래 문장에 오타가 있어도 새로 선택한 대상만 조사한다.
`네`와 같은 단순 동의로는 대상을 확정하지 않는다.
`네, payments-service요`, `payments-service로 해 주세요`는 원래 질문을 이어가는
선택으로 인식한다. 오타나 `아마 payments-service일 거예요` 같은 불확실한 응답에서는
다시 선택을 안내하고 원래 질문을 보존한다.

`취소`는 확인 대기를 해제한다. 새 증상이나 일반 대화는 새 요청으로 처리한다.
정상 완료 후에는 대상을 다음 질문에 암묵적으로 재사용하지 않는다.
조사가 실패하면 원래 질문을 남겨 같은 시스템 선택으로 재시도할 수 있다.
저장소를 다시 열어도 같은 thread_id의 확인 대기는 유지된다.
확인 요청마다 고유 request_id를 부여하고, 완료할 때 그 ID가 일치하는 행만 삭제한다.
문장이 같은 새 요청도 이전 진단의 완료 처리로 삭제되지 않는다.
기존 DB에 request_id 열이 없으면 질문과 대화 이력을 유지한 채 열과 ID를 추가한다.
현재 웹 화면은 새로고침 시 새 thread_id를 만드는 기존 동작을 유지한다.

## 실행 경계

- 그래프의 준비 노드에서 확인 대기를 재개하고, 진단 대상 확인 노드에서 불확실한 요청을 종료한다.
- 확인 대기 중에는 계획 모델, MCP 프롬프트/모니터링, 진단 RAG, 작성 모델을 호출하지 않는다.
  최초 요청의 chat/incident 분류 모델 호출은 유지한다.
- OpenAI·Ollama·Fake 계획은 같은 정규화 함수를 사용한다. 실행 직전 그래프도
  확정 목록을 강제하므로 모델이 다른 대상을 추가하거나 일부 대상을 누락할 수 없다.
- `/chat`과 `/chat/stream`은 같은 그래프를 사용한다.
  `TargetConfirmationRequired` 이벤트의 `choices`와 `suggestions`를 화면 버튼으로 표시한다.
- 한국어 별칭은 추천에만 사용한다. 임의의 자연어 별칭·모든 부정문을 의미적으로 해석하는 기능은 아니다.
- 알려진 오류 코드 형태(`ERR_…`, `ERROR_…`, `HTTP_…`)와 분위수 지표 형태는 예외로
  구분하며, 미등록 `…-service`나 시스템 이름 오타를 임의로 무시하지 않는다.
  `not confirmed`처럼 상태를 부정하는 표현은 대상 배제로 취급하지 않는다.
- 선택·재질문·취소·새 질문은 하나의 후속 응답 판별 함수에서 결정한다.
- 대상 없는 런북 조회 예외는 실제 제목과 지정된 조회 표현의 전체 일치에 한정한다.
  검색기 미주입 상태에서는 검색 설정 안내를 반환한다.
- 런북 제목은 그래프 생성 시 검색기가 이미 확보한 문서에서 가져온다.
  검색기 문서가 없는 비교 경로만 파일을 한 번 읽는다. 요청마다 파일을 다시 읽지 않으며,
  런북을 변경하면 검색 색인과 제목 목록이 함께 갱신되도록 실행 환경을 다시 생성한다.
- 계획 모델 호출은 유지한다. 이번 변경에 모델 호출 생략은 포함하지 않는다.
- 기존 비교용 `SUPERVISOR_VERSION=v1`은 변경하지 않았다. 이 기능은 v2에 적용된다.
- 보류 중인 실제 OpenAI 답변 스트리밍과는 별개이며, 기존 SSE 이벤트 계약을 사용한다.

## 검증

`tests/test_target_confirmation.py`는 대상 미지정·오타·복수 대상·모델의 잘못된 계획,
HTTP/SSE 간 재개, 취소·새 질문·스레드 격리, 저장소 재개와 실패 후 재시도를 검증한다.
`tests/test_app_runtime.py`에서는 실제 MCP 서버의 고정 모니터링 데이터를 조회하는 경로도 확인한다.
`tests/test_target_confirmation_review.py`는 검수에서 발견한 경계 입력, 동일 문장의 새 요청 보호,
기존 DB 이관, 요청 중 파일 미조회와 검색기 제목 일치를 검사한다.
